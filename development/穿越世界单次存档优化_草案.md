# 穿越世界单次存档优化（草案）

日期：2026-11-03。**状态：仅记录方案，未实装。安全性、接口可行性及目标速度均待验证。**

## 目标与边界

在交换机制不额外吞物品、不复制物品的前提下，尽量接近无感切换。性能以双方物品真正可以取用为完成标准。正常存档回退仍按游戏规则执行，不承诺保留上次有效存档之后的所有游玩进度。

推荐方向：**一次完整存档保存交换后的最终状态，再用小型提交记录确认结果。** 小记录只确认事务，不能作为脱离世界、玩家存档的独立补货依据。

## 保存顺序

现有流程：准备 → 保存准备状态 → 交换 → 保存交换结果 → 确认解锁。

拟定流程：

1. **锁箱并准备。** 双方冻结箱内容，校验格位、堆叠、皮肤和嵌套数据，验证接收物品能够恢复。原物品暂时保留；准备中的物品不可被玩家接触。
2. **准备最终快照。** 下一次完整存档中的箱内容采用交换后的结果，同时保存事务编号、原物品恢复记录及待确认标记。恢复记录只是数据，不作为第二份可取用物品生成。
3. **执行一次双层同步存档。** 箱内容、玩家状态和事务记录必须遵循同一次原生快照的保存顺序。双方确认相应结果已经写入前，均不解锁。
4. **持久化提交确认。** 双方写入小型提交凭证，绑定事务编号、世界会话和双方快照编号，核验写入结果。凭证的抗中断写入与恢复方式须先验证，不能仅凭发出写入请求认定成功。
5. **应用并解锁。** 按已验证的结果完成内存中的物品替换，双方确认后解锁。此时完整存档已包含最终箱内容，无需再保存整个世界。
6. **随正常存档收尾。** 后续存档记录物品取出、消耗及事务完成状态；仅在相关快照不再需要恢复记录时清理旧数据。

事务进入提交后，不因短暂超时擅自恢复原物品或切换保存方案。保存中的实际箱内容与快照内容暂时不同，是本方案最需要验证的部分。

## 异常恢复

| 情况 | 恢复原则 |
| --- | --- |
| 最终快照尚未写入时掉线 | 保留原物品；能确认双方均未提交时才安全取消，否则继续锁定核对 |
| 只有一层保存成功 | 不开放待交换物品；核对箱版本与快照编号后继续，无法证明一致时保留记录并锁定保护 |
| 双方快照已保存，提交确认中断 | 根据双方有效记录继续确认；提交结果不明确时不猜测成功或回滚 |
| 最终确认丢失、消息重复或乱序 | 重发确认；同一事务只应用一次，不重新生成已经装载的物品 |
| 解锁后取出、拆堆、合成，再崩溃 | 以实际加载的世界、玩家快照及事务标记为准；旧日志不得再补发已消耗材料 |
| 单层旧回档或日志与快照不匹配 | 锁定保护，保留证据，必要时恢复同一时间的双层备份；不能用未来凭证覆盖旧存档 |
| 物品加载或保存失败 | 保持锁定并保留恢复记录；不能把“没有收到确认”直接当成“没有执行” |

核心约束：重启加载到交换后的箱内容时，恢复流程只完成事务确认；不能再次覆盖箱子或追加旧物品。正常回档时，材料与合成产物也必须遵循同一存档时间线。

## 预期速度

| 方案 | 速度 | 依据与限制 |
| --- | --- | --- |
| 当前事件驱动版本 | 中位约 2.83 秒 | 本机独立双层小世界三轮实测，保留两次完整存档 |
| 单次最终快照＋小型提交记录 | 先争取约 1～2 秒 | 架构粗估，未实测；仍有原生约 1 秒存档调度等待及写盘、通信开销 |
| 后续专用快速协调保存 | 争取健康连接下亚秒级 | 研发目标，未验证；需证明能用前置协调替代固定等待，同时保持原生保存顺序与快照一致性 |

大存档、慢磁盘、高延迟及异常恢复可能明显更慢。不能通过提前显示新箱内容、实际仍锁箱来计作“无感完成”。

## 实装前验证与回退策略

- 验证最终快照与实际交换后的完整容器状态一致，包括附属组件、皮肤和嵌套物品；校验原生保存回调、小记录写入、玩家保存及快照编号的真实语义。
- 在每个消息与保存边界注入单层/双层进程终止、丢包、重复、乱序和写入失败；覆盖自动存档、退出保存与交换保存并发。
- 覆盖取出、拆堆、合并、合成、玩家退出/迁移后崩溃，检查材料、产物和事务记录恢复到一致时间线。
- 复杂物品或不兼容容器在交换开始前选择现有保护流程；已进入提交的事务必须按原协议完成或进入保护状态。
- 先验证单次存档方案，再研究专用快速保存入口；若原生接口无法满足一致性要求，保留固定等待，不以削弱物品保护换取速度。

当前实现与实测依据见 [穿越世界事务机制实装说明](穿越世界事务机制_实装说明.md)。本草案不代表批准修改保存接口或发布新版本。
